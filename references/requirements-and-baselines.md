# 需求、约束与有效基线

用途：新任务启动、目标变化，或发现既有实验不可比较时读取。内容来源于方法总结第二章、第三章和第四章的基线部分。

## 需求：在什么场景改善什么

| 项目 | 要确认的决策 |
| --- | --- |
| 对象与范围 | 算法、单算子、算子组合、单层、整模型或系统；输入何时可用，结果何时算完成 |
| 目标负载 | 形状、类型、分布、有效长度、padding、冷/热状态、已有缓存、到达方式、并发、用例权重 |
| 目标指标 | 延迟、首结果时间、吞吐、峰值空间、能耗、面积或成本；主次顺序 |
| 收益和验收 | 目标幅度、允许回退、资源上限、投入价值；无明确门槛时不自行编造“必须快X%” |

目标指标与解释指标分开：降低延迟是目标，提高带宽利用率可以是手段。性能门槛与“越快越好”的偏好也分开记录。

## 六类约束

| 类别 | 检查内容 |
| --- | --- |
| 功能与数值 | 数学语义、bitwise或误差标准、累加/舍入/近似规则、特殊值、边界、状态更新及可重复性 |
| 外部接口 | 形状、类型、布局、stride、对齐、ABI、覆盖与别名、数据可用时刻、兼容性、预处理及workspace |
| 硬件可行性 | 指令与类型、向量/矩阵形状、容量、bank/端口、粒度、通路、带宽、在途数、队列、事件与可见性语义 |
| 运行环境 | 设备、镜像、各时钟域、编译器/驱动/runtime、权限、共享负载、驻留条件、温度与持续运行状态 |
| 验收验证 | 必需用例、独立参考、目标平台与边界、允许回退、所需证据及复现承诺 |
| 工程交付 | 可改模块、软硬件边界、专用路径与通用路径、依赖、预算、复杂度、移植、版本和交付方式 |

先从项目中核实，再询问重要缺项。记为已知、待确认或不适用；未知不能视为没有限制。资源容量按物理对齐和同时存活区间核算，不能只加逻辑数组大小。

区分四种陈述：希望少占内存是需求；最多可用多少是约束；现在占多少是现状；容量不足导致重复搬运是需要证据支持的瓶颈。

固定硬件可以使用已有单元、bank和运行模式；不能凭空增加端口。可修改硬件时，再把新增资源、互连、流水及物理实现放入候选，同时评价资源和实现代价。

## 建立基线

| 参照 | 作用 |
| --- | --- |
| 正确性参考 | 清晰可信，必要时高精度，不要求高性能；基线自身也需验证 |
| 原始性能基线 | 最初通过必需正确性检查的有效实现，用于累计收益 |
| 当前有效基线 | 最近接受的版本，用于本轮收益；失败候选不能替代它 |
| 理论/模型边界 | 估计剩余空间，明确假设与适用范围，不冒充实测 |

调查实现的计算与控制工作、数据位置与路径、资源映射及依赖。保存以下事实到项目既有记录，或采用 [manifest](../assets/experiment-manifest.json)：

1. 源码及依赖的不可变版本，实际构建/执行/校验命令。
2. 输入、golden、形状、数据类型、分布及初始状态；有生成配方时保存参数、工具与预期哈希。
3. 硬件、镜像、频率和模型配置；未知项显式标记。
4. 计时起止事件、包含开销、单位和时钟域，正确性与性能验收标准。
5. 已运行的结果和原始证据，未完成的验证及其影响。

正确性和必要目标指标足够时即可建立 baseline。模块统计和完整 trace 根据诊断需要补充，次数按 [测量与决策](measurement-and-decisions.md) 确定。

如果初始实现错误，保留故障记录，先修到有效 baseline 再计算优化收益；若只能恢复部分环境，声明实际可复现层级。现有格式能承载这些事实时，不迁移或重建实验系统。
